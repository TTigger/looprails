# DECISIONS.md — Architecture Decision Records

> Why this template is shaped the way it is. **Read this before changing architecture.**
> To overturn a decision, add a *superseding* record — do not silently edit the old one.
> Format per record: Context (why a decision was needed) / Decision / Consequences (trade-offs).

---

## ADR-001 — Source of truth: `.agents/` holds all content
- **Context**: To work across tools (Claude / Codex / Cursor / Gemini / local models), content scattered
  across each tool's proprietary files drifts out of sync.
- **Decision**: All content (rules / skills / agents / rubrics / hooks) lives in `.agents/`. `CLAUDE.md`
  is a single line: `@AGENTS.md`.
- **Consequences**: One source, no duplicate maintenance; each tool must reference / be configured to
  point at `.agents/`.

## ADR-002 — Zero symlinks
- **Context**: Symlinks are a hard barrier for non-developers and frequently break on Windows clones
  (permissions / turning into plain-text files). The primary maintainer runs Windows + macOS.
- **Decision**: No filesystem symlinks. `CLAUDE.md` uses `@import`; skills/subagents load via `AGENTS.md`
  references; `.claude/settings.json` is generated by bootstrap as a plain file.
- **Consequences**: Cross-platform safe, zero friction; cost is that we do **not** rely on a tool's native
  skill auto-registration — skills load by reference instead.

## ADR-003 — Done = dual gate, output always binary
- **Context**: A single judge (a test suite *or* an LLM) can be fooled by hallucination.
- **Decision**: Definition of Done = gate 1 (deterministic tests) **AND** gate 2 (acceptance judgement),
  both green. Every evaluation emits a binary pass/fail.
- **Consequences**: Most robust; diagnosis is actionable. Heavier setup — every task needs a
  machine-judgeable condition.

## ADR-004 — Native-first execution
- **Context**: By H1 2026 the major tools ship `/goal`·`/batch` (the Ralph loop). The loop, persistence,
  and parallel worktrees are now commodity features.
- **Decision**: Delegate the loop to native `/goal`·`/batch`. `loop.mjs` slims to: expand phase → tasks,
  assemble the `/goal` spec, persist results. Adapters only "invoke each tool's `/goal` + collect results."
- **Consequences**: Small maintenance surface; we inherit tool upgrades. Template value concentrates on
  the three things native does not provide (see README).

## ADR-005 — LEARN: structured memory store
- **Context**: Native `/goal` has no cross-session memory; it does not make the next goal smarter.
- **Decision**: Thin index `.agent-learnings.md` (tag → entry + summary) plus tag-partitioned entries under
  `.agent-learnings/entries/`, retrieved on demand.
- **Consequences**: Most scalable; heaviest to set up.

## ADR-006 — Retrieval: plain Markdown + tags
- **Context**: The maintainer's `paul-brain` is consistently pure Markdown + Git + CLI.
- **Decision**: Retrieve by tag / keyword + filename convention. Zero infrastructure, pure Git.
- **Consequences**: Weaker semantic matching. **Upgrade path (non-breaking)**: when entries exceed ~150 or
  retrieval starts missing, add a CLI that builds a semantic index (SQLite FTS / embeddings); the underlying
  Markdown does not change.

## ADR-007 — Task source: PHASES.md → tasks/
- **Context**: The maintainer's workflow is PRD → PHASES.md → implementation; we also want the parallel
  worktree payoff.
- **Decision**: `PHASES.md` defines the phase blueprint; the runner expands the current phase into
  `tasks/*.md` and dispatches them to worktrees (planning separated from execution).
- **Consequences**: Granularity is flexible and fits existing habits; the runner needs an expansion step.

## ADR-008 — Three evaluation modes
- **Context**: A "tests + checklist" dual gate only serves quantitative tasks.
- **Decision**: Three modes, chosen per task via its `Verification` field: gate1 tests / gate2a checklist /
  gate2b rubric score.
- **Consequences**: Covers both quantitative and qualitative work; the rubric mechanism needs design
  (see ADR-009).

## ADR-009 — Qualitative eval: pairwise + screenshot + anchored rubric
- **Context**: An LLM acting as a qualitative judge is noisy, drifts, and can be fooled by surface polish.
- **Decision**: Rubrics use **anchored descriptions** + **tunable weights** → composite → threshold → binary.
  **Default to pairwise** (better than the best prior attempt) rather than absolute scores, and **judge the
  rendered screenshot artifact**, not the source code.
- **Consequences**: Much higher reliability; requires render / multimodal judging. Rubrics are living files =
  the personal benchmark, with weights tuned over time.

## ADR-010 — Adaptivity: guided calibration, soft layer only
- **Context**: New users often do not know what to do (blank-page problem); but opaque auto-learning bakes in
  early misjudgements, fights the "thin and maintainable" principle, and hits the Gloaguen finding that
  auto-generated context files reduce success.
- **Decision**: `/calibrate` runs interactive onboarding that **drafts** `AGENTS.md` constraints + initial
  rubric weights, written only after the user **confirms / edits**. Adaptivity touches the **soft layer only**
  (rubric weights / style preferences / rules), never the **hard spine** (tests must pass, constraints must hold).
- **Consequences**: Lowers the barrier while staying transparent and controllable; personalization cannot drift
  the core gates over time.

## ADR-011 — Human-readable PHASES, machine-strict tasks
- **Context**: `PHASES.md` is hand-authored by users (so it must be readable), yet the runner and the
  deterministic `scope-guard` hook need a strict, parseable representation.
- **Decision**: `PHASES.md` stays plain readable Markdown. An LLM-driven `expand-phase` skill generates
  strict `tasks/*.md` (machine-readable frontmatter — scope globs / eval_mode / rubric / depends — plus a
  five-part body). `loop.mjs` and hooks read only the generated files.
- **Consequences**: Humans never write YAML; machines never parse human prose. Cost: an expansion step whose
  output quality must be guarded by the skill (the right place to lean on the LLM under native-first).

## ADR-012 — Language layering (English engine room + bilingual README)
- **Context**: The template will be published on GitHub. Full dual-language duplication would re-create the
  drift problem solved by single-source-of-truth.
- **Decision**: Layer by reader, not by duplicating files. AI-facing / structural files (`AGENTS.md`,
  `.agents/*`, `DECISIONS.md`, the `PHASES.md` scaffold, script comments) are **English** (max model
  compatibility + ecosystem norm + open-source reach). `README.md` (English default) ships with a
  `README.zh-TW.md` companion. User-authored content (filled `AGENTS.md` fields, per-project phases, learning
  entries) is in **whatever language the project uses**.
- **Consequences**: Engine room has zero drift; only the README exists in two versions; users are not locked
  into a language for their own content.
